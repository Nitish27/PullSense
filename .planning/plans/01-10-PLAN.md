# Plan: Setup Center And Onboarding Health

**Goal:** Give PullSense testers a safe, self-service settings page that explains local integration readiness and the exact path to a first successful review.
**Phase:** D / settings, onboarding, and trust polish
**Requires:** `.planning/plans/01-09-PLAN.md`
**Provides:** A read-only setup status API plus a `/settings` onboarding surface.
**Context budget:** 3 tasks, approximately 90 minutes total

---

### Task 1: Add A Safe Setup Status API

**Files:**
- Create: `apps/api/src/routes/setup-status.ts`
- Create: `apps/api/src/routes/setup-status.test.ts`
- Modify: `apps/api/src/app.ts`
- Modify: `apps/api/src/env.ts`
- Modify: `apps/api/src/env.test.ts`

**Action:**
Add `GET /setup-status` using the existing Fastify route-registration pattern. Return a typed, additive read-only response that contains no secret values and reports only safe statuses for: database bootstrap, Redis queue configuration, GitHub App credentials, webhook signing posture, and Gemini provider configuration.

Expose whether the webhook uses the development default without returning the configured secret. Preserve current development defaults and do not make network calls to GitHub, Redis, Gemini, or PostgreSQL from this endpoint. Pass sanitized setup status into `createApp` through an explicit option so tests can supply deterministic states.

Test the default/missing/configured combinations and assert that no API key, private key, webhook secret, or database URL appears in the response. Do not add write endpoints, new dependencies, environment variables, or GitHub App mutations.

**Verify:**
```bash
pnpm --filter @ai-code-review/api test -- setup-status.test.ts env.test.ts
pnpm --filter @ai-code-review/api typecheck
```

**Done when:**
- [x] `/setup-status` reports safe readiness states with concise guidance.
- [x] Development webhook defaults are labelled as development-only, not production-ready.
- [x] Responses never contain secret values or connection strings.
- [x] API tests cover configured, missing, and development-default states.

### Task 2: Add The Settings Data Loader And Route

**Files:**
- Modify: `apps/web/src/review-runs.ts`
- Modify: `apps/web/src/review-runs.test.ts`

**Action:**
Extend the existing server-side web data utilities with a Zod schema and `loadSetupStatusPageData`. Fetch `${NEXT_PUBLIC_API_BASE_URL}/setup-status` with `cache: "no-store"`, returning the same explicit ready/error state style used by PR and repository-health routes.

Prepare the server route inputs using `getWebEnv`, `APP_NAME`, and `APP_PHASE`; the route itself ships with its dedicated view in Task 3 so this intermediate task remains independently buildable. Invalid API responses and non-OK responses must render a user-facing, non-sensitive error state. Do not add client-side fetching, a new API client library, or any settings write action.

**Verify:**
```bash
pnpm --filter @ai-code-review/web test -- review-runs.test.ts
pnpm --filter @ai-code-review/web typecheck
```

**Done when:**
- [x] The route loads setup status from the local API at request time.
- [x] Network, HTTP, and schema failures are represented as an explicit page error state.
- [x] Tests cover success and failure behavior.

---

### Task 3: Build The Read-Only Setup Center

**Files:**
- Create: `apps/web/app/settings/page.tsx`
- Create: `apps/web/src/setup-center-view.tsx`
- Modify: `apps/web/src/review-runs-dashboard.module.css`
- Modify: `apps/web/src/review-runs-view.tsx`
- Modify: `apps/web/src/repository-health-view.tsx`

**Action:**
Build `/settings` using the existing PullSense CSS module, typography, card, badge, and `next/link` conventions. Present service readiness with clear configured/development-attention/missing states, then provide a compact onboarding checklist: configure credentials, start local services, expose `/webhook`, install the GitHub App, and open or synchronize a PR.

Include an explicit trust note that the page never displays secret values and cannot change GitHub App settings. Add discoverable Settings links from the command center and repository-health surfaces. Design error and all-ready states for desktop and mobile without adding charts, client state, or new dependencies.

**Verify:**
```bash

pnpm --filter @ai-code-review/web typecheck
pnpm --filter @ai-code-review/web test
pnpm --filter @ai-code-review/web build
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

**Done when:**
- [x] A new tester can see what is ready, needs attention, or is missing without reading logs.
- [x] The page contains a clear first-review path and a safe-data trust note.
- [x] Settings is discoverable from the existing dashboard and repository health page.
- [x] The full workspace verification suite passes.
